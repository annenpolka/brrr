> **設計の中心：原文と取得記録を蓄積し、解釈を作り直せるようにする。その上で、HDDへ渡す入力だけを実験ごとに固定する。**
>

本文の「事実」は参照資料から確認した内容に限る。「推測（示唆）」は原因についての仮説である。第2章以降は、特記がない限り**未実装の設計提案**であり、既存機能の説明ではない。設定値、コマンド、ディレクトリ名、サンプルIDも提案である。

### 決定概要

| 決定 | 今回採る方針 |
| --- | --- |
| 保存の単位 | Issueだけでなく、コメント、PR、コードなどを独立した資料として保存する |
| 再利用の単位 | 関連資料を束ねた「調査事例（Case）」を使う。資料と事例を一対一に固定しない |
| 実験との境界 | 永続コーパスと、採用条件・分割・表示を固定した実験スナップショットを分ける |
| 正解の扱い | 正解を収集しないのではなく、入力側に公開する権限を分ける |
| 信頼性 | 保存、品質審査、漏洩審査、実験への採用を別状態にする。省略時は不採用ではなく未審査 |
| 初期実装 | ファイルの不変オブジェクト保存＋SQLite＋CLI。GitHubの読み取り専用収集から始める |

### 読み順

実装前の合意には第1〜3章、実装には第4〜10章、旧実験の移行には第11章、完了判定には第12〜14章を使う。参照資料は第16章に集約する。

この確認は「既存の全経路で必ず誤投入される」という証明ではない。**上記の保存・出力関数だけでは、意図した制約が強制されない**ことを示すものである。

また、`REAL_SOURCE_BACKED`、再現済み、独立した障害件数は同じ概念ではない。151パケットを151件の独立した再現済み障害として扱わない。

### 1.2 推測（示唆）

**仮説A：検索と圧縮が、既に有望だった型への収斂を増幅した可能性がある。**

後半の同型出力と、標本105のように原因を先に説明する入力は、この仮説と整合する。ただし、検索対象の偏り、圧縮方法、発明モデルの傾向を分離した比較実験は確認できていない。「収集だけが原因」とは結論しない。[R1][R5]

**仮説B：役割をプロンプトで分けるだけでは、公開境界の保証にならない。**

正解用ファイルを別ディレクトリに置いても、本文や `packet.json` に同じ情報が残り、出力側がそこへアクセスできれば境界を越える。対策は注意書きの追加ではなく、入力の許可リストと実際のアクセス制限である。[R2][R3][R4][R5]

**仮説C：次回の効率は新規収集量より、保存済み資料を再加工できる割合に左右される。**

原文があれば表示方法と採用条件を変えられる。要約しか残っていなければ、要約の正しさを後から検証するために再取得が必要になる。このため、収集量と再利用可能量を別指標にする。

## 2. 目的・対象範囲・非目標

### 2.1 目的

同じ収集基盤を、次回以降のHDD実験でも使えるようにする。具体的には、以下の操作を独立して可能にする。

| 操作 | 意味 |
| --- | --- |
| 収集 | 定義した探索範囲から資料を取得し、出典と取得結果を保存する |
| 再開 | 中断したジョブを、確定済み成果を再利用して続ける |
| 更新 | 元Issueなどの現在の状態を取得し、新しい版として追加する |
| 再加工 | 保存済み資料から、新しい抽出・分類・表示を生成する |
| 再選別 | 同じコーパスを別の採用条件で選ぶ |
| 再出力 | 固定済みスナップショットから同じ入力バイト列を出力する |

### 2.2 今回の対象範囲

対象は、資料の発見、取得、保存、関連付け、証拠の整理、表示の作成、品質・漏洩審査、スナップショット確定、HDD用入力の出力までである。

HDD固有の知識は末端のアダプターに置く。汎用コーパスの内部に `R1_DREAM`、PATH導入判定、候補ツールの採否などを埋め込まない。

### 2.3 非目標

発明プロンプト、R1のモデル選定、Reality Gate、ツール実装、Destroyer、候補の収益性・有用性評価は再設計しない。外部コードを実行する再現ランナーも今回の実装対象外とし、別工程から渡された実行証拠を受け取る契約だけ定義する。

一般公開データセット、全GitHubの網羅収集、ベクトルDB、Web UI、複数ホストへの分散実行、自律的な検索戦略の自己改変は初版に入れない。

### 2.4 成功条件

最初のパイロットは、旧標本の取り込み結果から**目標24事例**を扱う。これは初期検証の規模であり、統計的な十分性を意味しない。条件を満たす事例が不足した場合は、数を埋めず不足を報告する。

成功とは、中断と再実行で論理的な二重登録が起きず、各入力の由来を追跡でき、漏洩や不足を未審査のまま通さず、固定済み入力をネットワークなしで再出力できることである。HDDの新規ツール数は、収集基盤の初期完了条件にしない。

## 3. 設計原則と境界

### 3.1 不変条件

| ID | 不変条件 |
| --- | --- |
| INV-01 | 取得した原文は、通常の更新で上書きしない |
| INV-02 | 原文に「誰かがそう書いた」ことと、その内容が実験で確認されたことを区別する |
| INV-03 | 要約、分類、原因推定、難易度は一次資料ではなく版付き派生物とする |
| INV-04 | 取得エラー、意図した取得制限、結果0件を同一視しない |
| INV-05 | 保存成功は、品質合格やHDD投入許可を意味しない |
| INV-06 | 漏洩審査と実験採用は、審査対象の内容ハッシュに結び付く |
| INV-07 | 正解の開示許可と、過去実験のアイデアの開示許可を分離する |
| INV-08 | 確定済みスナップショットは更新しない。変更時は新しいIDを作る |
| INV-09 | 同じ障害・派生系列が、発見用と未知事例評価用にまたがることを防ぐ |
| INV-10 | LLMの再実行結果が同じになるとは仮定せず、生成結果そのものを保存する |
| INV-11 | 取得側には読み取り権限だけを与え、資料中のコマンドを実行しない |
| INV-12 | 再現済みと表示するには、対象版・環境・手順・実行結果の証拠が必要である |

### 3.2 三つの層

```text
GitHubのIssue / コメント / PR / コード
                 ↓ 発見・取得
[永続コーパス]
  原文オブジェクト・取得履歴・版・事例・関連・解釈・証拠
                 ↓ 表示生成・審査・選別
[実験スナップショット]
  採用母集団・採否理由・分割・固定した版・公開範囲・ハッシュ
                 ↓ HDD adapter
[実験入力]
  許可した本文・素材・seedだけを含む隔離されたバンドル
```

これは論理フローであり、サービスを三つ起動する設計ではない。初版は一つのローカルCLIとSQLiteで実現する。

### 3.3 保存構造

```text
src/brrr_corpus/                 # 新しい収集・保存・選別モジュール
  adapters/github/              # 資料取得
  adapters/hdd/                 # HDD入力への変換
schemas/                        # 版付きのデータ契約
recipes/collection/             # 何を探し、何を取得するか
recipes/experiments/            # 何を選び、何を見せるか

.brrr-corpus/                   # 実データ。原則としてGit管理外
  corpus.sqlite                 # メタデータ、版履歴、ジョブの正本
  objects/sha256/                # 原文・実行証拠・生成物の不変バイト列
  staging/                      # 未確定の一時生成物
  quarantine/                   # 漏洩・機密情報などの隔離資料
  exports/                      # 入力バンドルと操作用の出力

lab-runs/<run-id>/
  collection-snapshot.json      # 固定したsnapshotへの参照
  inputs/                       # 許可リストから出力した入力だけ
  collection-report.md          # 母集団・採否・不足・検査結果
```

SQLiteは単なる再生成可能キャッシュではなく、**資料・版・関係・ジョブ状態の正本**とする。`objects/` はそれらが参照する不変バイト列の正本である。両方を一貫した組としてバックアップする。JSON/YAML出力は交換・監査用であり、同じ属性を別の正本として二重管理しない。

公開するGit差分は原則としてコード、schema、recipe、設計、最小テストfixtureに限る。第三者の全文、未加工ログ、資格情報を含み得る取得記録を自動でコミットしない。

## 4. データ契約

### 4.1 主要エンティティ

| エンティティ | 主な内容 | 更新方法 |
| --- | --- | --- |
| `Source` | 内部ID、provider、資料種別、provider側ID、親資料、URLの別名 | 同一性を保ち、URL変更などは履歴として追加 |
| `SourceRevision` | source ID、原文hash、取得レスポンス内の位置、providerの作成・更新日時 | 原文が変われば新しい版を追加 |
| `FetchAttempt` | 対象、取得日時、HTTP結果、許可したヘッダー、本文hash、エラー | 試行ごとに追加 |
| `AcquisitionRevision` | ある資料群について取得できた範囲、未取得範囲、取得開始・終了 | 再取得ごとに追加 |
| `CaseRevision` | 調査事例、資料集合、対象環境、症状、関係、証拠参照 | 解釈・束ね方の変更で新しい版を追加 |
| `Claim` | 主張、種別、原文範囲、生成経路、確信度、公開分類 | 入力版と生成器を固定した新しい主張を追加 |
| `EvidenceRecord` | 実行対象、環境、コマンド、ログ、exit status、観測主体 | 証拠単位で追加 |
| `ViewRevision` | 公開モード、入力Claim、ファイル一覧、生成器、出力hash | 再生成時に別の版を追加 |
| `Review` | 審査種別、対象hash、判定、理由、審査者・設定 | 審査ごとに追加 |
| `SelectionRun` | 候補母集団、recipe、採否理由、重複・分割判断 | 選別実行ごとに追加 |
| `Snapshot` | 採用した各版、分割、公開範囲、manifest hash | 確定後は不変 |
| `Job` / `Exposure` | 実行状態・再開情報／どの入力をどこへ公開したか | 状態遷移・公開イベントを記録 |

「更新可能なコーパス」とは、以前の事実を消すことではなく、**新しい観測と解釈を追加できるコーパス**を指す。

### 4.2 IDと版

内部の `source_id` と `case_id` は不変のUUIDとする。外部IDは `(provider, resource_kind, provider_id)` の一意制約で解決する。URLや `owner/repo` の文字列だけを同一性の根拠にしない。外部ID未取得の旧資料は仮登録し、ID取得後に対応付ける。

Issue番号とPR番号が同じでも、Issue側の会話資料とPR側の差分・レビュー資料を区別する。同じPRから来た資料群という関係を持たせ、事例件数を増やすために二重計上しない。

`blob_id` は保存バイト列のSHA-256とする。原文レスポンスは正規化せず保存する。正規化JSONや本文抽出は別オブジェクトとし、元レスポンスとJSON Pointerなどで結ぶ。メタデータだけの変更も版として追えるようにする。

生成JSONのcanonicalization、文字コード、改行、並び順は `serialization_version` で固定する。ハッシュ前に原文のUnicodeや改行を勝手に揃えない。

### 4.3 時刻と履歴の限界

少なくとも以下を別々に持つ。

| フィールド | 意味 |
| --- | --- |
| `provider_created_at` | providerが報告した作成日時 |
| `provider_updated_at` | providerが報告した更新日時 |
| `observed_at` | 収集器がその内容を取得した日時 |
| `acquisition_started_at / finished_at` | 複数ページ・資料の取得期間 |
| `content_available_at` | その版が過去の時点に存在したと裏付けられる日時。わからなければnull |

GitHubのコメントAPIは現在の本文と作成・更新日時を返す。[G4] 本設計では、それだけを根拠に編集前本文を復元できるとは扱わない。

たとえば作成が1月、編集が3月、取得が4月のコメントを、作成日時だけで「2月時点の入力」に含めない。過去の版が保存されていなければ `HISTORICAL_CONTENT_UNVERIFIED` とし、厳密な時点制約のある表示から除外する。

複数APIの取得を単一時点のトランザクションとも扱わない。`Snapshot` が固定するのは**実際に保存した内容の集合**であり、「GitHub全体のその瞬間の状態」ではない。

### 4.4 証拠の軸

旧 `kind` は `legacy_kind` として保存し、次の軸へ自動的に格上げしない。

| 軸 | 値の例 | 判定の意味 |
| --- | --- | --- |
| 由来 | `real` / `derived` / `synthetic` / `unknown` | 実報告由来か、加工・生成されたものか |
| 確認 | `reported` / `source_inspected` / `failure_observed` / `paired_observed` | 報告、コード確認、失敗観測、失敗側と修正側の双方の観測 |
| 対象 | `upstream` / `reduced_fixture` | 元OSSを実行したのか、縮約fixtureを実行したのか |
| 観測主体 | `reporter` / `maintainer` / `local_runner` | 誰の実行か |
| 修正参照 | `unknown` / `candidate` / `verified` | 参照を知っているだけか、関係を検証したか |
| 取得充足 | `complete_for_policy` / `partial` / `unavailable` | 宣言した資料取得範囲を満たしたか |

`paired_observed` には、失敗側と修正側の双方の版、環境、手順、期待結果、実際の結果が必要である。PRの親SHAを取得しただけでは `failure_observed` にしない。縮約fixtureの成功を元OSSの再現成功へ読み替えない。

### 4.5 主張と原文の対応

実験入力に含める事実的な主張には、次のいずれかを要求する。

`legacy_claim` は旧標本にしか残っていない未照合の主張であり、原文確認済みの観測としては公開しない。

`reporter_observation` は報告者の発言、`local_observation` は保存した実行結果、`source_fact` は特定版のソースに直接確認できる性質を表す。`analysis` はコードや複数資料からの解釈、`hypothesis` は未確認の推測である。

各Claimは `source_revision_id + locator`、または `evidence_id` を持つ。根拠位置のない生成文を観測欄へ入れない。合成した問題設定や問いは `generated_prompt` として識別し、実際の報告であるかのように装わない。

原文範囲の指定は、たとえばJSON Pointerと、その値をUTF-8化した文字列のバイト範囲とする。範囲の意味はschemaで固定し、元文字列のhashも照合する。

## 5. 発見と取得

### 5.1 検索recipeと実験recipeを分ける

収集recipeは「どこから何を取るか」を定義する。実験recipeは「保存済みの何を使うか」を定義する。後者の条件に合わない資料でも、取得済み原文を削除しない。

検索レーンは初版で三つに限定する。

| レーン | 狙い | 例 |
| --- | --- | --- |
| 機構起点 | 既知の失敗系統を深掘りする | キャッシュ、順序依存、同名の解決、emptyとunset |
| 症状・調査起点 | 原因がまだ名付けられていない困難を拾う | 単体では通る、CIだけ失敗、再起動で直る、無出力で成功扱い |
| 対照枠 | 既存の有望系統への集中を検知する | あらかじめ指定したリポジトリ・期間の広いbug候補枠 |

対照枠もGitHub全体の無作為標本ではない。限定した取得母集団の中から固定seedで抽出したものとして記録する。

OPEN/CLOSEDは収集時の一律除外条件にしない。未解決でも情報量のある事例を保存し、解決済み対照を必要とする評価recipeだけが修正証拠を要求する。

### 5.2 GitHubへの検索

GitHubの検索APIは一検索で最大1,000件を返し、検索タイムアウト時に `incomplete_results` を返す。また認証方式によってIssueとPRを別クエリにする必要がある。[G1]

初版では常にIssueとPRを明示的に分け、生成したクエリ文字列、API version、パラメーター、検索レーン、日時、レスポンスhashを保存する。検索結果の本文断片だけで資料取得を完了としない。

取得対象をリポジトリと作成期間で区画化する。1,000件へ達した区画や `incomplete_results=true` の区画は、期間・リポジトリなどでさらに分割する。それでも解消できなければ `TRUNCATED` または `INCOMPLETE` として残す。対象リポジトリを網羅的に列挙できていない場合は、世界全体の網羅を宣言しない。

検索区画には次を記録する。

```yaml
# 構造を示す架空の例。実際に収集した結果ではない。
partition_id: example-partition-01
query_recipe_hash: example-recipe-hash
lane: symptom
resource_kind: issue
window:
  field: created_at
  start_inclusive: '2025-01-01T00:00:00Z'
  end_exclusive: '2025-02-01T00:00:00Z'
scan_epoch: example-epoch-01
state: INCOMPLETE
last_committed_request_id: example-request-02
next_request: null
incomplete_results_seen: true
coverage_claim: enumerated_search_results_only
```

境界をAPIの包含範囲へ変換する場合は重なりを許し、保存時に一意IDで重複を除く。検索上の並び順は明示するが、並び順を固定しただけでライブAPIが不変になるとは仮定しない。

### 5.3 取得する資料

初期取得ではIssue本体と本文コメントを取得する。PRが関連する場合は、PRメタデータ、会話コメント、レビュー・行コメント、変更ファイル情報を別資料として扱う。Issue一覧にPRが含まれ得ることを考慮して、資料種別を識別する。[G5]

関連するコードは、選別・審査に必要な範囲を固定SHAで取得する。添付資料や外部リンクは自動で無制限に辿らない。recipeに深さ、許可ホスト、MIME、件数、バイト数上限を定義する。初版の関連リンク展開は明示的なIssue–PR関連を中心とする1段階とし、それを超えるものは保留する。

本文コメントを取得できても、レビューや添付が未取得なら、その不足を `AcquisitionRevision` に記録する。上限到達は失敗でも全件取得でもなく `PARTIAL_BY_POLICY` とする。

### 5.4 ページングと取得完了

ページングはレスポンスの `Link` など、APIが返す継続情報に従う。[G3] HTTP adapterは本文だけでなく、必要なレスポンスヘッダーを保存できなければならない。

一つのページについて、原文オブジェクト、資料ID・版、次ページ位置を保存し終えてからcheckpointを進める。次ページ位置だけを先に保存しない。本文が欠損・切り詰められていた場合は確定しない。

`complete_for_policy` は「recipeで要求したendpoint・ページを取得し、既知の欠損がない」という意味に限る。削除済み資料、未提供の編集履歴、検索インデックスの未反映まで回収できたことを意味しない。

### 5.5 ライブデータの更新

再開では、保存済みページの後続から継続できる。ただし、ページ番号やcursorを保存するだけでは途中の編集・削除によるページ移動に対応できない。このため区画終了時と更新時に、重なりを持つ再走査を行う。

更新用watermarkは最大の `updated_at` ではなく、**連続して完了した範囲の末尾**とする。失敗した区画を飛ばしてwatermarkを進めない。初期の重なり期間は24時間を仮置きし、長期遅延を拾うための対象全体の再走査も用意する。24時間は欠落防止の保証値ではない。

既知Issueの本文・コメント・PR資料は、Issue本体の更新日時だけに依存せず、設定した期限で再検証する。増分探索と既知資料のrefreshを別ジョブにする。

### 5.6 HTTP制御とエラー

初版のHTTP要求は共有キューで直列化し、LLMの並列worker数と分離する。検索と通常取得の制限を区別し、実際のヘッダーに従って待機する。条件付きリクエスト、レート制限時の待機、再試行はGitHubの推奨に合わせる。[G2]

| 結果 | 処理 |
| --- | --- |
| 200、未変更 | 新しい取得観測を記録し、同じ内容オブジェクトを再利用 |
| 200、変更あり | 新版を追加し、過去版と既存snapshotを保持 |
| 304 | 対応する検証済みキャッシュを参照し、取得観測を追加。キャッシュがなければ未解決 |
| 403 / 429 | レート制限か権限不足かを区別。待機可能なら `next_retry_at` を保存 |
| 404 | 不可視・移動・削除などを未確定のまま記録。即座に「削除された」と断定しない |
| 5xx / timeout | 上限付きbackoff。最後の試行でも失敗したら要介入として保留 |
| 不正なJSON / 本文切り詰め | パース失敗として原文とエラーを保持。正常完了扱いにしない |
| 上限超過 | 制限の種別と未取得範囲を記録し `PARTIAL_BY_POLICY` |

リダイレクトは許可ホストを検証して辿り、URLの別名を残す。アクセストークンを別ホストへ引き継がない。認証ヘッダーは保存対象外とする。

## 6. ジョブ・再開・保存の整合性

### 6.1 状態を分ける

取得ジョブの状態は、資料品質や実験への採否と混ぜない。

```text
PENDING → LEASED → RUNNING → SUCCEEDED
                     ├──→ RETRY_WAIT → PENDING
                     ├──→ BLOCKED
                     └──→ FAILED_FINAL
```

`SUCCEEDED` はそのジョブの契約を完了した意味である。資料不足のある取得revisionを正常に記録したジョブもあり得るため、取得充足は別属性として参照する。

品質審査は `PENDING / PASS / HOLD / REJECT`、漏洩審査は `PENDING / PASS / FAIL / INDETERMINATE`、実験採否は `SELECTED / EXCLUDED / DEFERRED` とする。一般的な `READY` 一つに統合しない。

### 6.2 冪等性

ネットワーク要求やLLM処理は、失敗時に複数回実行され得る。保証するのは「各処理が一度しか走らない」ではなく、**同じ成果が複数回到着しても、同じ論理成果として一度だけ確定すること**である。

ジョブの冪等キーは、stage、入力版・hash、recipe hash、実装version、scan epochから作る。新しい取得観測を作るrefreshは別epochとする。生成物の再試行は同じjobのattemptとして記録し、異なる出力を無言で上書きしない。

LLM要求が送信された後に応答を失った場合、料金まで厳密に一回へ抑えるとは保証しない。attemptとprovider request IDを保存し、再試行による重複コストを把握できるようにする。

### 6.3 Leaseと遅延worker

workerは期限付きleaseと単調増加するfencing tokenを取得する。期限が切れたjobは再取得可能とするが、古いworkerの結果は、現在のtokenと一致しない限り確定させない。

生成されたオブジェクトを残すことと、jobを成功へ遷移させることを分ける。遅延した旧workerの生成物は監査用に保存できても、現在の結果を上書きできない。

初版は単一ホスト・一つの調停プロセスを前提とする。複数のエージェントは成果を返すが、checkpointや採用状態をそれぞれ勝手に更新しない。

### 6.4 書き込み順序

1. `staging/` にバイト列を書き、hashとサイズを検証する。
2. オブジェクトを同一ファイルシステム上で不変領域へ原子的に移す。同じhashが既存なら内容を照合して再利用する。
3. SQLiteの一つのtransactionで、資料・版・取得結果・job結果・checkpointを確定する。
4. snapshotの出力は一時ディレクトリで完成させ、全検査後に公開する。

オブジェクト保存後にDB確定が失敗した場合は孤立オブジェクトが残り得る。逆に、DBから未完成オブジェクトを参照する状態を作らない。GCは参照整合性検査と猶予期間を経て行い、初版では自動削除しない。

OSクラッシュを含む耐久性を確認する際は、単なるrenameだけでなく、必要なflush・fsync・SQLiteの設定を含めてテストする。

### 6.5 再開の契約

`resume` は未完了・再試行可能・期限切れleaseのjobだけを対象にし、確定済みの版やsnapshotを変更しない。生存中のleaseを奪わない。schemaやrecipeが途中で変わった場合は、自動的に同じjobとして続けず、明示的な移行または別jobを要求する。

停止理由、試行回数、最終エラー、次回試行可能時刻を残す。取得不能を大量の空データへ変換して成功に見せる実装を禁止する。

## 7. 事例の構成・重複・選別

### 7.1 Issueではなく調査事例を束ねる

`Case` は、症状、環境、調査時の観測、試行した対処、関連コード、修正候補を結ぶ単位である。

一つのIssueに複数の障害が含まれる場合は複数Caseへ分けられる。一つの障害がIssue・PR・別のIssueに分かれる場合は一つのCaseへ束ねられる。最初から原因を一つに断定する必要はなく、関連が未確認なら候補関係に留める。

収集直後の暫定Caseも保存してよい。束ね方を変えたら `CaseRevision` を追加し、以前の実験が参照した束ね方は保持する。

### 7.2 重複には二種類ある

| 関係 | 処理 |
| --- | --- |
| 同一資料を再取得 | Sourceの同一性を解決し、取得観測または新版を追加 |
| 同一障害の重複報告 | Case間に `same_incident` を記録し、審査後に統合または同一グループ化 |
| 派生・縮約・対照fixture | 元Caseとの `derived_from` を保持 |
| 別環境で起きた同じ機構 | 別Caseとして保持し、`same_mechanism` で関連付け |
| 似ているだけ | `possible_duplicate` としてレビュー待ち |

同じ修正コミット、似た題名、embeddingの近さだけで自動統合しない。一つのPRが複数の障害を直す場合もある。誤統合を戻せるように、関係の追加・取消も版付きで記録する。

「同じ機構の別事例」は転用検証に使えるため、単なる重複として捨てない。

### 7.3 品質審査と集合の選別

第一段階では、Case/View単体の品質を判定する。出典、原文との対応、観測と解釈の分離、取得不足の明示、理解に必要な文脈が対象である。

第二段階では、その実験へ加える意味を判定する。機構、症状、調査上の困難、観測方法、エコシステムの広がりを見て、現在の集合へ追加される違いを評価する。

**品質が高くても、その実験では重複として除外され得る。逆に、珍しいだけで品質不足を通してはいけない。**

分類が未確定のものは `unknown` のまま扱う。多様性の数字をよく見せるために、似た事例へ細かい別ラベルを付けない。主分類と複数の補助タグを分け、分類基準と版を固定する。

### 7.4 採否理由

採否記録には最低限、candidate revision、view revision、recipe hash、判定、理由コード、根拠参照、審査者を含める。

```text
SOURCE_MISSING           原文や必要資料が不足
ACQUISITION_PARTIAL      要求した取得範囲が未完了
PROVENANCE_GAP           主張から根拠へ辿れない
INSUFFICIENT_CONTEXT     表示だけでは状況を理解できない
ANSWER_LEAK              非公開情報が入力に混入
HISTORICAL_UNVERIFIED    必要時点の本文を保証できない
DUPLICATE_INCIDENT       同一障害として別項目を採用
GROUP_SPLIT_CONFLICT     同じ系列が分割をまたぐ
EVIDENCE_NOT_ELIGIBLE    その用途に必要な証拠状態でない
DIVERSITY_CAP            集合内の集中上限に到達
BUDGET_DEFERRED          品質ではなく資源配分上の保留
```

`REJECT` や `EXCLUDED` でも原文は削除しない。後から別recipeで使う可能性を残す。追加取得などで解消できる不足は `HOLD` または `DEFERRED` として、解消条件を記録する。

### 7.5 HDDの結果を戻す場合

HDDの結果は `Outcome` として別に記録できるが、既存の品質審査や原文を上書きしない。薄いラッパーが出たことだけで、そのCaseを恒久的に低品質としない。

初版では結果から検索recipeを自動変更しない。機構起点・症状起点・対照枠の比較を見て、人間が次のrecipeを版付きで変更する。収集の良否とモデル出力の良否を同じ点数へ押し込まない。

## 8. 表示生成と正解漏洩の防止

### 8.1 二つの公開モード

| モード | 目的 | 公開する内容 |
| --- | --- | --- |
| `blind_problem` | 原因を伏せた発明・未知事例評価への入力 | 審査済みの症状、環境、観測、失敗側コード、許可した対照条件 |
| `investigation_open` | 既知の調査から、次回の手間を減らす道具を考える入力 | 原因・修正を含めた調査過程。既知解を開示したことを明示 |

二つを同じ実験条件として集計しない。初版のHDD adapterは `blind_problem` のみ必須とし、`investigation_open` は同じコーパスから別recipeで生成できる拡張点とする。

原因を知っている資料を捨てる必要はない。**保存範囲と公開範囲を別々に決める。**

### 8.2 公開分類

資料やClaimは、単なる「正解ファイルか否か」ではなく次の公開分類を持つ。

| 分類 | 例 |
| --- | --- |
| `candidate_public` | 観測ログ、環境、報告者の症状説明 |
| `restricted_solution` | 原因解説、修正差分、修正後に追加されたテスト |
| `restricted_evaluation` | 評価用の正解、隠しテスト、採点に使う情報 |
| `restricted_prior_ideas` | 過去実験の候補ツールや評価結果 |
| `unreviewed` | まだ公開区分を確定できていない内容 |

`candidate_public` は自動的な公開許可ではない。時点制約や用途によって、さらに審査する。修正前のコメントでも原因を明かしている可能性があるため、時刻だけで盲検性を保証しない。

### 8.3 生成手順

Compressorを自由要約器ではなく、根拠付きの表示生成器として扱う。

1. 元資料からClaim候補と根拠範囲を抽出し、観測・分析・推測を分類する。
2. 公開分類と実験recipeで、入力に使えるClaimを確定する。
3. 表示生成器には許可したClaimと素材だけを渡す。正解全文を渡して「忘れる」ことは要求しない。
4. 生成された事実的な各文をClaimへ対応付け、対応がない文は修正または非事実的な問いとして分離する。
5. 完成した入力バンドル全体を品質・漏洩審査へ渡す。

原文を読む抽出役は正解を知り得る。だからこそ、その出力に公開審査を挟み、最終生成役の入力を制限する。役割名だけで情報境界ができたと扱わない。

モデル名・設定・プロンプトhash・入力hash・出力hash・parser versionを保存する。temperatureを固定しても同じ生成結果を保証しない。再出力には保存済みの生成物を使う。

### 8.4 漏洩審査

漏洩審査は次の三段階で行う。

| 段階 | 検査内容 | 限界 |
| --- | --- | --- |
| 構造検査 | 不許可ファイル、path traversal、外部symlink、正解フィールド、未審査素材、混在したモード | 言い換えた内容の判定はできない |
| 決定的な照合 | 非公開span、修正SHA・URL・テスト名などの識別子、既知の禁止情報との一致 | 識別子だけでは誤検出も起こる。意味的な同義表現を取りこぼす |
| 内容レビュー | 根拠より先の原因断定、修正後の知識、別事例のgold由来情報の混入 | 人間・LLMとも完全な検出器ではない |

正解を見られるレビュー役の出力は、違反の位置と理由コードを中心にする。正解文を含む診断ログを、修正対象の公開入力へ自動挿入しない。詳細は隔離領域に残す。

意味的レビューが未実施・判定不能なら `INDETERMINATE` とし、初期パイロットでは人間の審査が解消するまで確定しない。完全一致チェックを通過しただけでは `PASS` にしない。

### 8.5 独立した開示ポリシー

```yaml
# ポリシー構造の例
answer_policy:
  scope: view_revision
  mode: blind_problem
  solution_access: denied
  evaluation_access: denied
prior_ideas_policy:
  scope: experiment_run
  access: denied
```

`FIRST_SELECTION.md` や実験フェーズの変更によって、正解の検査をまとめて解除しない。過去案を解禁するときはそのポリシーだけを変更し、正解を開示したいときは別モード・別snapshotを作る。

いずれのレビューも対象hashへ結び付ける。本文、ファイル名、recipe、exporterが変わったら、以前の合格判定を流用しない。

### 8.6 入力の隔離

HDDへ渡すのは許可リストから構築したバンドルだけにする。原文アーカイブ、`packet.json`、正解、curationの詳細、収集ログ、他の標本、`.git` を同じ作業領域に置かない。

ローカルconsumerには、入力バンドルだけを読み取り可能にし、出力領域を別に与える。strictな盲検を主張する場合は、親ディレクトリやネットワーク経由で正解を読めないことも検証する。

既存consumer側でこの隔離ができない場合でも、静的なバンドル検査には価値がある。ただし `isolation_level: static_bundle_only` と記録し、「環境全体で正解へアクセスできない」とは主張しない。公開OSSに対するモデルの事前知識まで消せるとも主張しない。

## 9. 実験スナップショットとHDD adapter

### 9.1 スナップショットに固定するもの

| 対象 | 固定内容 |
| --- | --- |
| 母集団 | 選別時点で列挙した候補CaseRevisionと適格性 |
| 収集範囲 | 取得recipe・epoch・完了／未完了区画・取得不足 |
| 入力の版 | SourceRevision、Claim、ViewRevision、素材hash |
| 採否 | 全候補の判定、理由、重複判断、集合制約 |
| 分割 | discovery / holdoutなどの用途、系列グループ、固定seed |
| 変換 | 抽出・前処理・表示・exporterの版と設定 |
| 審査 | 品質、漏洩、アクセス境界の判定と対象hash |
| 公開 | 実際に配布する各ファイル名・サイズ・hash |

`latest`、可変ブランチ、更新される外部URLだけへの参照を確定manifestに残さない。URLは出典追跡のために残し、再出力は保存済みバイト列から行う。

### 9.2 分割と既知情報

同一障害、重複報告、派生、縮約・対照fixtureの関係を連結したグループ単位で分割する。機構が同じだけの独立事例は自動的に同一グループへまとめない。

関係が曖昧なものは保守的に同じグループへ寄せるか、未知事例評価から外す。実験間で資料を再利用する場合は、過去にどのviewがどのconsumerへ公開されたかを `Exposure` に残す。

何に対して未知なのかを `exposure_scope` で固定する。初期パイロットでは当該実験のdiscovery工程を範囲とし、その工程へ既に公開されたCase系列はholdoutに入れない。過去の実験への公開は別に記録し、「人間も含め過去に一度も見たことがない事例」とは称しない。

古い実験について公開履歴を確認できなければ `exposure_unknown` とする。新しい乱数seedで分割し直すだけで「未知」と呼ばない。freshな実行contextと、過去資料へのアクセス制限も実験側の責任として明示する。

### 9.3 多様性の初期値

24事例のパイロットでは、主機構の同一clusterを最大8事例、同一repositoryを最大6事例とする案を採る。これは経験的に最適化した値ではない。重複グループを除いた独立Caseを分母にする。

ラベル不明を別々のclusterとして数えない。`unknown` も一つの枠として可視化する。複数タグの副次的な集中も報告し、主ラベルの付け替えで集中上限を回避しない。

条件を満たせなければ不足理由付きのドラフトを出す。自動的に上限を緩和しない。深掘り目的で同型を増やすときは、別の `focused` recipeとして明示する。

holdout比率は初期目標25%とするが、系列グループの境界を優先するため件数を厳密に6件へ揃えることは要求しない。修正前後の比較を行う用途では `paired_observed` など追加条件を要求し、満たさないholdoutをバグ修正評価用と称しない。

### 9.4 確定と再出力

```text
DRAFT → RESOLVED → VALIDATED → SEALED
```

`RESOLVED` で各版と母集団を固定し、`VALIDATED` で参照・hash・審査・分割・集合制約を確認する。`SEALED` 後に内容を変えない。問題発見時は、旧snapshotを失効扱いにするイベントと、修正版snapshotを追加する。

`snapshot_id` はcanonical manifestのhashとする。確定作業の時刻や取得実行の可変情報は、hash対象の内容manifestとは別のreceiptへ置く。manifestにはhashへ自己参照を入れない。

既存の出力先へ再出力するときは、同一のファイル集合とhashなら再利用し、異なる内容があれば拒否する。既存ディレクトリへ新しいファイルだけを足す方式は採らない。

再出力は保存済みviewと素材を使い、ネットワーク要求・LLM呼び出しを行わない。同じsnapshotとexporter版から同じファイル名とバイト列が得られることをテストする。ZIPなどの梱包物まで同一にする場合は、梱包順・タイムスタンプ・権限も固定する。

### 9.5 HDD adapterの契約

```text
入力: SEALED snapshot + adapter version
出力: 検査済みのTASK / OBSERVED / COMMANDS / 素材 / seed
禁止: raw corpusや旧packetを直接探索して、不足を自動補完すること
```

発明のためのHDD指示は既存の意図を保持した版付きテンプレートとして管理し、今回の収集基盤の変更と発明プロンプトの変更を同時に行わない。

旧 `compile_seed.py` の連結方式は参考にできるが、そのまま安全なAPIとは扱わない。新adapterはartifactの許可リスト、証拠区分、審査対象hashを確認してから出力する。[R4]

`OBSERVED` は「報告者が観測」「ソースから確認」「この環境で実行」を区別して表示する。コマンドにも `reported / proposed / executed` を付ける。ローカル実行していない資料に「このcheckoutで確認済み」といった定型文を付けない。

Dreamer向け表示には、詳細な採用理由、機構の正解ラベル、修正URL、内部Case名など、問題を先回りするメタデータを原則含めない。必要な追跡情報は公開バンドルの外に対応表として持つ。

## 11. 旧HDD回からの移行

### 11.1 基本方針

`lab-runs/specimen-hdd-20260902-1112/` と `.hdd-runs/specimen-hdd-20260902-1112/` は、実験の履歴として変更しない。旧スクリプトを履歴ディレクトリ内で書き換えるのではなく、新しい収集器・adapterへ必要な処理を移す。

旧 `specimen-013` などの番号は `legacy_alias` として残す。新しい永続IDと対応付けるが、番号から独立した障害件数を推定しない。

最終報告の151パケットを期待値として照合する。[R1] 移行時に実際のディレクトリ・ファイルを再列挙し、差があれば報告する。報告書へ数字を合わせるために架空項目を作らない。

### 11.2 移行段階

| 段階 | 処理 | 完了条件 |
| --- | --- | --- |
| M1 棚卸し | 標本・ファイルの一覧、hash、サイズ、旧ID、旧manifestを取得 | 元ファイルに変更がなく、件数差と欠損が説明される |
| M2 保全インポート | 全旧ファイルを `legacy_artifact` として保存し、aliasを作る | 再インポートしても論理的な二重登録がない |
| M3 出典の整理 | URL、provider ID、固定SHA、元資料・派生関係を照合 | 不明をunknownのまま残し、出典対応を追跡できる |
| M4 原文回収 | 不足するIssue本文・コメントなどを現在の状態で取得 | 回収時刻と、過去版ではないことが記録される |
| M5 再加工・審査 | Claim・Viewを作り直し、品質と漏洩を審査 | 審査を通過した新しい版だけが出力対象になる |
| M6 パイロット | 目標24事例を選別し、固定入力を再出力する | 第12章の必須テストを満たし、不足・偏りを報告できる |

### 11.3 旧フィールドの扱い

| 旧データ | 移行先・扱い |
| --- | --- |
| `manifest.yaml` | 原文を保存。パース結果は別の派生物として保存 |
| `REAL_SOURCE_BACKED` | `legacy_kind` に保存。原文の実在・取得充足を別に検査 |
| `source_issue / source_pr` | Sourceの候補参照。同じPRの別表記なら関係を整理 |
| `failing_ref / fixed_ref` | 旧実験が主張した参照として保存。存在確認・修正関係・実行確認を分ける |
| `raw-sources/SOURCE.md` | 内容を確認し、原文なのか、出典一覧・要約なのかを分類 |
| `TASK / OBSERVED / COMMANDS` | 旧Viewとして保全。新しい一次資料とは扱わない |
| `answer-key/` | 非公開資料として保存 |
| `packet.json` | 正解を含み得る非公開の旧artifactとして保存。公開入力へ直接流さない |
| `files/` | 旧素材として保存し、出自、hash、重複、不要な残存物を検査 |
| `curation.md` | 旧審査記録として保存。新しい内容hashへの合格判定には転用しない |

**回収した原文が現在の版しかない場合、それを2026-09-02当時の原文として扱わない。** `recovered_at` を記録し、旧入力の完全再構築と、現在資料からの再加工を区別する。

旧artifactに欠けている情報を推定で埋める場合は `legacy_inference` とし、確認済みの出典・観測欄へ混ぜない。

### 11.4 標本105の具体的な移行例

標本105には、公開エラー、コードの因果説明、修正後のテスト名、ローカル非実行の記載が同居している。[R5] これを一つの「観測」として移行しない。

| 内容 | 新設計での扱い |
| --- | --- |
| 公開された `deno i` のエラー | 原文を回収・照合できれば `reporter_observation`。旧packetだけなら `legacy_claim` |
| 共有依存が削除されるという因果説明 | 根拠範囲付きの `analysis`。盲検表示では公開可否を審査 |
| 修正後のテスト名と修正差分 | `restricted_solution` |
| ローカル実行していないこと | 実行証拠なしとして保持。再現済みに格上げしない |
| 元のTASK・OBSERVED | 旧入力のまま不変保存 |

新しい `blind_problem` viewには、確認できた症状と必要な失敗側素材を入れる。原因説明を削ると問題として成り立たない場合は、別の観測を取得するか `INSUFFICIENT_CONTEXT` で保留する。原因だけを隠した、解読不能な断片を作ることは目的ではない。

### 11.5 旧コードとの対応

| 旧コード | 継承する要素 | 置き換える要素 |
| --- | --- | --- |
| `emit_specimen.py` | 分かりやすいファイル出力構成 | 暗黙採用、自由文字列manifest、同じ場所への上書き、正解入りpacketの共有 |
| `contamination_check.py` | 決定的な文字列照合という安価な検査 | 全体解除、正解ファイルだけを境界とする扱い、完全一致のみでの合格 |
| `compile_seed.py` | HDDが読む素材の組み立て | 未審査素材の連結、実行状態にかかわらない定型表現、書き出し後だけの検査 |

移行中に旧実験を読み出す経路が必要でも、新しい公開adapterを経由させる。安全境界を整える前に、旧factoryをそのまま次のrunへ接続しない。

## 12. 検証計画と受け入れ条件

### 12.1 テストの層

保存・再開・schema・公開境界は、合成fixtureと固定したHTTP応答で決定的にテストする。実際のGitHubへの契約テストは小さく限定し、通常のテストをネットワーク状態へ依存させない。

意味的な漏洩や文脈の十分性は自動テストだけでは決まらない。合成した漏洩パターン、旧標本の監査、独立した内容レビューを併用する。

### 12.2 必須テスト

| ID | 入力・故障条件 | 合格条件 |
| --- | --- | --- |
| T01 | 同じページ・同じ旧runを2回取り込む | Source、同一revision、legacy aliasが二重登録されない |
| T02 | オブジェクト保存直後、DB確定前に停止 | 再開で回収でき、checkpointが先へ飛ばない |
| T03 | DB確定直後、worker応答前に停止 | 再試行しても同じ論理成果が再登録されない |
| T04 | lease切れ後、旧workerが結果を返す | fencing token不一致で現在の状態を上書きしない |
| T05 | 同じコメントが後から編集される | 新版と取得観測が増え、旧snapshotの入力hashは変わらない |
| T06 | 304と、対応キャッシュの欠損 | 正常時は再利用。欠損時は空本文として成功させない |
| T07 | 403、404、429、timeout、不正JSON | 原因を区別し、空の検索結果に変換しない |
| T08 | 検索上限到達・`incomplete_results` | 分割または未完了記録。網羅済みと表示しない |
| T09 | ページ間で追加・削除・並び替えが起きる | 重複排除と再走査が働き、coverageの限界を記録する |
| T10 | コメント取得中に上限到達・中断 | 本体だけをもって全資料取得済みとしない |
| T11 | Issueと関連PR、同一障害の別報告 | 資料数と事例数を分け、関係を保存する |
| T12 | 同機構の独立事例 | 誤って同一障害へ統合しない |
| T13 | 修正SHAはあるが実行ログがない | `paired_observed` やローカル再現済みにならない |
| T14 | 旧 `curation` が省略／`ACCEPT_R1` だけ存在 | 新品質審査は `PENDING` のまま |
| T15 | 正解が本文、題名、テスト名、ファイル名に混入 | 構造・識別子・内容レビューで違反fixtureを検出 |
| T16 | 正解を言い換えて混入 | 意味的レビュー用fixtureで検出を評価し、未判定を通さない |
| T17 | `FIRST_SELECTION.md` を追加 | 正解漏洩審査の挙動が変わらない |
| T18 | 審査後に本文・素材・exporterを変更 | 旧PASSが失効し、再審査が必要になる |
| T19 | `../`、絶対パス、外部symlink、残存ファイル | 公開ディレクトリ外へ出ず、許可リスト外は出力されない |
| T20 | 同じ系列がdiscoveryとholdoutへ入る | 分割検査で停止する |
| T21 | 原文がsolution公開後に編集されたものしかない | 厳密な時点制約のあるviewへ無条件で入らない |
| T22 | ネットワークを無効にして同じsnapshotを再出力 | ファイル集合とバイト列hashが一致する |
| T23 | 外部資料に「命令を実行・正解を出力せよ」と書く | データとして扱われ、取得権限・公開許可が変わらない |
| T24 | 多様性上限や必要証拠を満たす候補が足りない | 不足を報告し、自動緩和・捏造・未審査投入をしない |
| T25 | SQLiteとオブジェクトをバックアップから復元 | 参照整合性が成立し、確定snapshotを再出力できる |
| T26 | discovery工程へ公開済み、または公開履歴不明の候補 | exposure policyに従いholdoutから除外し、理由を残す |

T15/T16でテストfixtureを検出できても、未知の意味的漏洩を完全に防げる証明にはならない。パイロットでは公開予定の全viewを内容監査し、見逃しと過剰削除を記録する。

### 12.3 合成fixture

合成データは「原文に見える偽物」を本番コーパスへ混ぜるためではなく、収集器の故障条件を制御するために使う。テスト用namespaceと `origin: synthetic` を必須にする。

最低限、コメント編集、同時更新、途中ページ欠損、PRとIssueの重複、削除・不可視、レート制限、巨大添付、post-fixのテスト名、言い換えた正解、同一系列のsplit漏洩、prompt injectionを含む小さなfixtureを用意する。

再現ランナーを実装しない段階でも、実行証拠の良い例・不足例・対象SHA不一致例を生成して、証拠の格上げ条件を検証する。

### 12.4 パイロットの受け入れ判定

公開する全入力で、事実的な主張から根拠への参照が解決し、必須の品質・漏洩審査がPASSであり、対象hashが一致することを要求する。既知の正解混入、同一系列の分割越境、失われた素材への参照は0件でなければならない。

これは「未知の誤りも0件」を意味しない。原文が報告者の誤認を含む可能性、未発見の重複、意味的漏洩は残るため、監査範囲と残余リスクをreportへ残す。

旧パケット全部が公開適格になることは要求しない。**全部を保全できることと、全部を使えることを混同しない。**

## 13. 実装順序と最小構成

### 13.1 段階別の成果物

| 優先 | 作業単位 | 成果物と完了条件 |
| --- | --- | --- |
| P0 | 新しい公開境界 | 旧runを変更せずに使える安全なadapter。暗黙採用なし、公開許可リスト、hash結合、正解ポリシー独立、原子的出力。T14〜T19を先に実装 |
| P1 | コーパスと旧run import | 不変オブジェクト、SQLite、Source/Revision、旧alias、原文と旧解釈の区別。取り込み再実行と棚卸しを確認 |
| P2 | GitHub収集と再開 | recipe、区画、HTTP記録、checkpoint、refresh、制限・エラー処理。T01〜T10を確認 |
| P3 | Case・Claim・View・審査 | 出典範囲、証拠軸、関連、品質審査、盲検表示、漏洩審査を実装 |
| P4 | snapshotとパイロット | 母集団固定、採否理由、グループ分割、確定・再出力・監査。目標24事例で一連の操作を完了 |

P0は「漏洩を完全自動で検出するAI」を先に作る意味ではない。初期段階は人間の内容審査を受け取り、それが対象内容に紐付いていない限り公開しない薄い境界でよい。

### 13.2 初版で小さく保つ部分

第4章のエンティティは論理契約であり、それぞれを独立サービスや巨大なテーブル群にする必要はない。版付きJSON payloadと、ID・hash・状態・検索に使う少数の列から始める。schema検証と一意制約は省略しない。

最初はHTTP並列度1、ローカルSQLite、固定したrepository一覧、lexical search、手動審査でよい。semantic search、embedding dedupe、高度な自動分類は必要性が測定できてから追加する。

Collectorが制御するのは取得・保全・公開条件であり、エージェントの思考過程ではない。自由度が必要な分析は派生物として隔離し、保存と公開の規律は決定的なコードに寄せる。

### 13.3 実装担当への開始条件

最初に対象コミットと本設計を固定し、旧runの内容hashを記録する。P0の負例テストを書いてから新adapterを作る。その後、旧標本の一部でimportと再出力を通し、全標本へ広げる。

未確認の問題を一括修復した巨大コミットにせず、保存・公開境界、import、取得、表示、snapshotの順に分離する。それぞれに対応するテストと移行ログを付ける。

新しい外部Issueを大量に集めるのは、同じ資料の再取り込み、取得失敗、正解の混入を正しく扱えることを確認してからにする。

## 14. 運用指標と運用手順

### 14.1 指標

| 領域 | 指標 | 数え方・注意 |
| --- | --- | --- |
| 取得 | 資料数、原文revision数、取得完了区画、未完了区画 | パケット数と混同しない |
| 事例 | 独立Case数、同一障害グループ数、派生数 | 使用した重複判定版を付ける |
| 根拠 | 根拠参照が解決する主張数／入力中の事実的主張数 | 報告内容の真偽を保証する指標ではない |
| 品質 | PASS/HOLD/REJECT、理由別件数 | 予算不足と品質不足を分ける |
| 漏洩 | FAIL/INDETERMINATE、監査での見逃し・過剰削除 | 自動検査PASSだけを成功率にしない |
| 多様性 | 主機構・補助タグ・症状・調査方法・repository分布 | `unknown` を明示する |
| 再利用 | 原文再取得なしで再加工できたCaseの割合 | 旧要約だけからの再生成を同等に数えない |
| 再開 | 重複抑止件数、失敗job、最長保留、復旧後の整合性 | worker稼働率最大化を目的にしない |
| 資源 | API要求・bytes・LLM費用／公開適格な独立Case | 試行の重複コストも含める |
| 再現性 | オフライン再出力hash一致率 | 確定snapshotを分母にする |

HDDのツール新規性や採用本数は別reportに置き、収集品質と対照して分析できるようにするが、同じ総合スコアへ混ぜない。

### 14.2 一回の収集・出力手順

収集recipeとrepository一覧を固定し、planを確認する。collectを実行し、終了時に完了区画・不足・保留を確認する。必要ならresumeし、更新を取りたい場合だけrefreshを開始する。

取得した資料からCase・Claim・Viewを作り、品質と漏洩を審査する。実験recipeで候補母集団を固定し、採否理由と分割を確認する。validateを通過したsnapshotだけsealし、ネットワークを使わずにHDD入力をexportする。

最後にDBとオブジェクトの一貫したバックアップを作り、snapshotからの復元・再出力を試す。HDD側に公開したviewとsnapshot IDをExposureへ記録する。

### 14.3 停止・更新・事故

| 状況 | 操作 |
| --- | --- |
| 中断・worker停止 | checkpointとleaseを確認しresume。元ファイルを手で消してやり直さない |
| 元資料の編集 | refreshで新版を追加。既存snapshotはそのまま |
| 分類や圧縮を変えたい | reprocessして新しい派生版を作る |
| 採用条件を変えたい | 新recipeから新snapshotを作る |
| 公開済み入力の漏洩を発見 | 対象snapshotを失効扱いにし、影響する実験を列挙。修正版を新IDで作る |
| 資格情報・私的情報を発見 | 隔離し、公開・同期を停止。必要な削除と影響記録を優先する |
| DBとobjectの不整合 | exportを停止し、整合性監査とバックアップ復元を行う |

通常の不変保存には、資格情報の除去や必要な削除という例外を設ける。削除対象の内容を監査ログへ再掲せず、削除イベントと影響したsnapshot IDを残す。そのsnapshotが再出力不能になった場合も、制約を隠さない。

## 15. 判断理由・見送る案・残る限界

### 15.1 設計判断

| 判断 | 採用理由 | トレードオフ |
| --- | --- | --- |
| 原文と解釈を分ける | 圧縮や分類を作り直し、出典へ戻れる | 保存容量と関連メタデータが増える |
| Caseを導入する | Issue/PRの重複と複数障害を扱える | 束ね方の審査が必要になる |
| 正解を保存して公開を制限する | 漏洩検査や別用途で再利用できる | アクセス分離を実装する必要がある |
| 既定値を未審査にする | 不足や省略がそのまま採用にならない | 初期の処理速度は下がる |
| SQLiteと不変ファイルを使う | 一人・単一ホストの運用に収まり、transactionと検査を使える | 複数ホストへの拡張は別設計になる |
| 意味的レビューを必須にする | 完全一致では拾えない原因説明を検査する | コストと判定のばらつきが残る |
| 検索の網羅を限定的に表現する | APIの上限やライブ更新を誤魔化さない | 母集団の厳密な代表性は保証できない |
| 出力hashを固定する | モデルや外部資料の更新から実験を切り離せる | 生成器を変えると新しい版・審査が必要になる |

### 15.2 今回見送る案

Scoutを増やすだけの対策は採らない。根拠の保存や公開境界を直さずに並列度を増やすと、同じ型と同じ誤りを速く蓄積する可能性がある。

「解決済みのIssueだけ」をコーパス全体の規則にはしない。修正比較用の実験には必要でも、発見用の資料収集まで狭める理由にはならない。

モデルに全資料を読ませてから正解を除いた要約を頼む一段構成を、公開境界の代替にはしない。モデルを利用する場合も、Claimの公開審査と最終バンドル検査を残す。

高度なエントロピー最適化や自律的な探索配分は初版では見送る。まず固定したレーン・上限・対照枠で偏りを測る。計測できない最適化を先に作らない。

### 15.3 保証しないこと

この基盤は、公開されたIssueの内容が真実であること、過去の編集履歴をすべて回収できること、検索で全障害を見つけること、LLMが事前学習で解を知らないことを保証しない。

また、良い事例を渡せば必ず新しい道具が生まれるとは限らない。保証する範囲は、何を集め、何を観測し、何を推測し、何を公開し、どの入力を使ったかを追跡し、同じ条件で比較できるようにすることである。

### 15.4 次の比較実験

収集基盤の完了後に、同じCaseに対する旧表示と新表示を比較する。旧表示に正解が含まれる場合は、その条件を明示した比較にする。モデルと発明プロンプトを固定し、その次に選別recipeだけを変えて比較する。

これは下流の発明実験であり、本設計の実装完了条件からは切り離す。検索・圧縮・選別を同時に変えて、何が改善したのかわからなくすることを避ける。
